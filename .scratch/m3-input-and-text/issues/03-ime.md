# IME

Blocked by: 02

## What to build

한글을 칩니다. **이 마일스톤에서 가장 어렵고 가장 늦게 발견되면 가장 비싼 항목입니다.**

`NSTextInputClient`가 붙고, `keyDown`이 IME에 먼저 기회를 줍니다. 소비되지 않은 키만 의미 이벤트가 되어 내려갑니다.

**marked text는 코어로 가지 않습니다.** 커서 위 Swift 오버레이로 그리고, 확정 시에만 UTF-8로 내려보냅니다. 미확정 텍스트는 터미널에 입력된 것이 아니며, 그리드에 넣으면 취소 되돌리기가 불가능해지고 PTY 부분 전송은 복구할 수 없습니다. 오버레이는 최상단 패스이고 셀 격자에 얹히지 않습니다.

**조합 중 여부는 IME가 소비하지 않은 키에도 실려 내려갑니다.** 엔진이 그 플래그로 조합 중의 특수키 처리를 바꾸는데, 없으면 엔진은 조합 상태를 알 방법이 없습니다. 조합 중 방향키가 IME에 갈지 터미널에 갈지 갈리는 지점이 여기이고, 틀리면 조합이 깨진 채 그리드에 들어갑니다.

후보창 위치는 스냅샷 커서 좌표에서 계산합니다. 뷰가 자기 커서를 따로 세지 않습니다.

**검증은 손으로 합니다.** 실제 입력기가 붙어야 도는 경로이고, [DoD C절](../../../docs/07-definition-of-done.md#c-ime-and-input)이 시나리오를 이미 서술하고 있습니다. 그것이 이 마일스톤 종료 기준의 절반입니다.

## Acceptance criteria

- [ ] 두벌식 조합 중 글자가 커서 자리에 인라인으로 보인다
- [ ] 조합 중 백스페이스가 자소 하나만 지운다
- [ ] 조합 중 Enter가 먼저 확정하고, Esc가 취소하며 그리드에 아무것도 남기지 않는다
- [ ] 조합 중 커서 이동 키의 IME 소비와 터미널 전달이 올바르게 갈린다
- [ ] 조합 미확정 상태에서 포커스를 잃어도 그리드가 오염되지 않는다
- [ ] 후보창이 커서 셀에 뜨고, 스크롤·리사이즈 직후에도 따라간다
- [ ] vim insert 모드 안에서, 그리고 tmux 안 vim에서 위 전부가 재현된다
- [ ] 일본어 변환 후보와 이모지 팔레트(⌃⌘Space)가 같은 경로로 들어간다
- [ ] DoD C절 7항의 통과를 스펙의 종료 기준에 기록한다

## 언제 무엇을 볼 수 있는가

배선은 섰고, 손으로 볼 수 있는 것과 아직 볼 수 없는 것이 갈립니다. **확정된
글자는 화면에 나타나지 않습니다** — `Atlas.bakeable`이 `0x21...0x7E`이고 그 밖의
코드포인트는 배경만 그려지므로, 확정된 한글은 빈 칸입니다. M2가 약속한 그림
그대로이며 [08](08-font-load-and-ligature-path.md)~[10](10-four-faces-and-line-cache.md)이
채웁니다. 조합 중 오버레이는 CoreText가 직접 그리므로 여기에 매이지 않습니다.

순서는 스펙대로 둡니다. 지금 도는 것을 지금 보고, 나머지는 글리프 경로가 선 뒤에
한 번에 봅니다.

지금 볼 수 있는 것 — 조합 중 인라인 표시, 자소 단위 백스페이스, Enter 확정과 Esc
취소, 조합 중 커서 이동 키의 갈림(셸 커서가 움직이는지로), 포커스 이탈 뒤 깨끗한
그리드, 후보창의 위치와 추적.

글리프 경로 뒤에 볼 것 — 확정된 글자가 두 칸을 차지하며 그리드에 남는 모습,
vim insert 모드와 tmux 안 vim에서의 재현, 일본어 변환과 이모지 팔레트의 확정 결과.

확정 경로 자체는 화면 없이도 확인됩니다. `echo 한글 > /tmp/k` 뒤 `wc -c /tmp/k`가
7을 답하면 한글 음절 둘의 UTF-8 여섯 바이트가 개행과 함께 그대로 셸에 들어간
것입니다. **2026-08-28에 확인했습니다** — 같은 화면에서 `echo`와 `>` 사이가 정확히
네 칸 비어 있었고, 그것이 엔진은 넓은 문자의 자리를 제대로 잡았으며 빠진 것은
글리프뿐이라는 증거입니다.
