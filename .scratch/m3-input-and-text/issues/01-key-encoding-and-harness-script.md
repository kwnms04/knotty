# 하네스 스크립트 형식과 키 인코딩

Blocked by: —

## What to build

키가 바이트가 됩니다. 그리고 그것을 검증할 이음매가 여기서 섭니다 — 이후 입력 티켓들이 전부 이 길을 씁니다.

경계를 건너는 것은 **판정되지 않은 키 이벤트**입니다. 물리 키(W3C `KeyboardEvent.code`), 수정자, 소비된 수정자, UTF-8, 조합 중 여부, 액션. 어떤 바이트가 나갈지는 코어가 정합니다 — 커서 키 모드, keypad 모드, Option-as-Meta, `modifyOtherKeys` 전부 엔진의 인코더가 세션 상태를 읽어 판단합니다. cf. [0017](../../../docs/adr/0017-semantic-input-events.md).

**하네스가 지금은 바이트 스트림만 재생합니다.** 입력 이벤트는 바이트가 아니라 표현할 수 없습니다. 출력 바이트와 입력 이벤트를 한 파일에서 번갈아 쓸 수 있는 형식을 더합니다. 하네스가 마지막에 서술하는 것은 지금과 같습니다 — 화면, 자식에게 갈 바이트, 이벤트 큐, wake 수. 자식에게 갈 바이트를 이미 서술하고 있으므로 비교 장치는 그대로입니다.

**이 형식이 필요한 이유가 곧 0017의 근거입니다.** 검증 대상이 "모드에 따라 갈리는 분기"인데, 모드를 켜는 것은 출력 시퀀스이고 그것에 반응하는 것은 입력 이벤트입니다. `DECSET 1` 을 먹인 다음 방향키를 보내는 것이 그 시나리오 전부이고, 둘이 한 파일에 없으면 재현할 수 없습니다.

Rust 단위 테스트로 ABI를 직접 두드리는 편이 싸지만, 이음매가 하나 늘고 골든이 아니어서 인코딩이 조용히 바뀌는 것을 막지 못합니다.

## Acceptance criteria

- [ ] 키 이벤트를 받는 심볼이 헤더에 있고, 생성된 헤더가 Rust 소스와 일치한다
- [ ] ABI 버전이 올라가지 않는다
- [ ] 하네스 녹화에 출력 바이트와 입력 이벤트를 번갈아 쓸 수 있다
- [ ] 같은 방향키가 커서 키 모드에 따라 다른 바이트를 큐에 넣는 것이 골든에 남는다
- [ ] 수정자 조합(⌃·⇧·⌥·⌘)이 각각 다른 바이트를 내는 것이 골든에 남는다
- [ ] 조합 중 플래그가 켜진 키 이벤트가 그렇지 않은 것과 다르게 다뤄진다
- [ ] 미식별 키가 조용히 성공하지 않고 구분되는 상태값으로 답한다
- [ ] 기존 녹화 5종의 골든이 그대로 통과한다
