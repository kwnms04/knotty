# 폰트 로드와 3단 경로 분기

Blocked by: —

## What to build

`❯`가 보이고 `!=`가 리거처로 보입니다.

아틀라스가 지금 `0x21...0x7E`로 잘려 있습니다. 그 범위를 넓히는 것이 이 체인의 첫 동작이고, M2에서 프롬프트의 `❯`(U+276F)가 빈칸이던 이유가 그것입니다.

셰이핑이 **3단 경로**로 갈립니다. 가르는 것은 셀과 글리프가 1:1로 남는가입니다 — fast path는 아틀라스 직접 조회, 리거처 경로는 1:1이 유지되는 셰이핑, slow path는 깨지는 나머지입니다. 뒤의 둘은 셰이퍼가 같고, 그것은 CoreText입니다. cf. [0018](../../../docs/adr/0018-coretext-shapes-the-ligature-path.md). 이 티켓은 앞의 둘과 **분기 자체**를 세웁니다. slow path는 09입니다.

**참여 집합·윈도우·오버행을 폰트 로드 시 GSUB에서 유도합니다.** 셋 다 같은 순회에서 나옵니다. 상수로 박지 않습니다 — 측정한 6종에서 집합이 13개부터 271개까지였고 서로 겹치지도 않았습니다. 측정된 최악값(13셀 윈도우, 4셀 폭 아틀라스 항목, 좌우 각 3셀 오버행)은 **초기 할당 힌트로만** 씁니다. 넘는 폰트는 재할당을 부르지 결함을 부르지 않습니다. cf. [0016](../../../docs/adr/0016-derive-the-ligature-path.md).

**로드 시 그리드를 단언합니다.** 프로브 문자열의 글리프 수가 문자 수와 다르면 그 폰트의 리거처 경로를 끕니다. 셀 수를 바꾸는 폰트는 그리드 모델을 무너뜨리므로, 화면이 깨지는 대신 리거처가 없어집니다.

`liga`와 `calt`를 함께 켭니다. 하나만으로는 폰트에 따라 리거처가 나오지 않습니다.

**렌더러 골든이 글리프를 부르는 법이 여기서 바뀝니다.** 지금은 코드포인트로 부르는데, 셰이핑이 들어오면 셀 하나가 코드포인트 하나로 결정되지 않습니다. 글리프 ID로는 부를 수 없습니다 — 폰트 버전에 따라 달라져 개발 기계와 CI 러너가 다른 답을 냅니다. **클러스터의 코드포인트들, 그 안에서 몇 번째 셀인지, 어느 경로를 탔는지**로 부릅니다.

유도가 내놓은 **수치는 골든으로 고정하지 않습니다.** 폰트의 성질이지 우리 코드의 성질이 아니고, 시스템 폰트는 macOS 버전에 따라 바뀝니다. 실제 수치는 `prototype/gsub-probe` 브랜치가 6종 33 face에서 이미 쟀으므로 다시 재지 않습니다.

## Acceptance criteria

- [x] `❯`처럼 ASCII 밖의 단일 코드포인트가 그려진다
- [x] 참여 집합·윈도우·오버행이 폰트 로드 시 GSUB에서 유도된다
- [x] `liga`와 `calt`가 함께 켜진다
- [x] `!=`·`=>`가 리거처로 그려지고 열 정렬이 어긋나지 않는다
- [x] 로드 시 그리드 단언이 돌고, 실패하면 그 폰트의 리거처 경로가 꺼진다
- [x] `liga`/`calt`가 없는 폰트에서 참여 집합이 비어 있다
- [x] 렌더러 골든이 클러스터·셀 순번·경로로 글리프를 부르고, 폰트 버전에 흔들리지 않는다
- [x] 유도 수치는 골든에 들어가지 않는다
