# 입력은 의미 이벤트로 내리고, 선택의 상태만 앱에 둔다

키·마우스·휠·포커스는 **판정되지 않은 의미 이벤트**로 FFI를 건너고, 인코딩과
정책 분기를 코어가 합니다. 예외는 선택 하나입니다 — 제스처의 상태(앵커, 클릭 수,
드래그 중인지)는 앱에 두고 경계 계산만 명령으로 내립니다.

## 맥락

M3이 입력 경로 전체를 배선합니다. 지금 헤더에 있는 입력은
[`kt_session_write`]와 [`kt_session_set_selection`] 둘뿐이라, 나머지는 전부
신설입니다. 무엇을 신설하느냐가 곧 이 결정입니다.

핀된 VT 엔진을 조사한 결과 **입력 경로 전체가 이미 엔진에 있습니다.**

| 엔진 심볼 | 덮는 범위 |
|---|---|
| `ghostty_key_encoder_*` | 키 인코딩. 옵션에 `MACOS_OPTION_AS_ALT`, `ALT_ESC_PREFIX`, `CURSOR_KEY_APPLICATION` |
| `ghostty_mouse_encoder_*` | 마우스 인코딩. `setopt_from_terminal`이 리포팅 모드를 터미널에서 직접 읽음 |
| `ghostty_focus_encode` | 포커스 리포팅 |
| `ghostty_selection_gesture_*` | 클릭 수·워드/라인/출력 단위·오토스크롤을 포함한 제스처 상태 기계 |
| `ghostty_terminal_select_word` · `select_line` · `select_word_between` | 경계 계산만 하는 단발 함수 |
| `ghostty_terminal_selection_format_alloc` | 선택 범위 → 텍스트 |
| `ghostty_terminal_resize` · `scroll_viewport` | 리플로우 · 뷰포트 이동 |

키 열거형은 W3C `KeyboardEvent.code`의 물리 키이고, 키 이벤트에
`set_composing`·`set_utf8`·`set_unshifted_codepoint`·`set_consumed_mods`가
있습니다 — `NSEvent`와 `NSTextInputClient`가 주는 것과 그대로 맞물립니다.

[05-swift-app](../05-swift-app.md)의 4절("TerminalView … 제스처 해석")과
7절("Option-as-Meta 판정은 그 직전 Swift에서")은 이 사실을 모르고 쓴 문장이며,
이 결정으로 고칩니다.

## 근거

**인코딩이 이미 엔진에 있으므로 판정도 함께 둡니다.**
[02-ffi](../02-ffi.md#input-path)가 "인코딩 자체는 VT 엔진이 수행합니다"라고
정했습니다. 판정만 앱에 남기면 같은 사실을 두 층이 나눠 갖게 됩니다 — 앱은
어떤 모드인지 알아야 분기하고, 코어는 같은 모드를 인코딩하려고 다시 읽습니다.

**앱으로 내보낸 모드 값은 한 프레임 뒤집니다.** 판정을 앱에서 하려면 마우스
리포팅 모드와 커서 키 모드를 스냅샷에 실어야 하는데, 스냅샷은 게시된 시점의
값입니다. 리포팅을 켜는 시퀀스가 도착한 직후의 클릭은 아직 옛 모드로
판정됩니다. 코어에서 판정하면 그 창이 없습니다.

**선택만 예외인 이유는 상태와 경계가 이미 다른 곳에 있기 때문입니다.**
제스처의 상태는 `NSEvent.clickCount`와 마우스 다운 시점의 셀이 이미 정확하게
들고 있고, 워드 경계는 엔진이 유니코드 규칙으로 이미 들고 있습니다. 각자 있는
곳에 두면 새로 만들 상태가 없습니다.

**선택 명령은 앵커와 현재 지점을 함께 받습니다.** 엔진에
`ghostty_terminal_select_word_between`이 따로 있고 그 헤더가 이유를 씁니다 —
단어를 더블클릭한 뒤 공백이나 문장부호 위로 끌 때 "포인터 아래 단어"만 잡는
구현은 선택이 깜빡이거나 무너집니다. 셀 하나만 받는 명령은 이 결함을 그대로
만듭니다.

## 기각안

**앱이 인코딩까지 한다.** 02-ffi를 정면으로 뒤집고, 커서 키 모드·수정자 규칙·
kitty 프로토콜 여부를 앱이 추적하게 됩니다. 엔진이 이미 맞게 하는 일입니다.

**엔진 제스처 상태 기계를 코어에 둔다.** 클릭 수와 앵커와 드래그 여부가 코어에
한 벌 더 생깁니다. AppKit이 세는 클릭 수와 코어가 세는 클릭 수가 어긋나는
종류의 결함이 가능해지고, 동결된 헤더에 이미 있는
`kt_session_set_selection`이 사장됩니다. 아끼는 것은 오토스크롤 방향 판정
한 줄인데, 틱을 만드는 타이머는 어느 쪽이든 AppKit에 남습니다.

**마우스 모드를 스냅샷에 싣는다.** 위의 한 프레임 지연이 이유입니다. 필드가
하나 늘면 구조체 레이아웃이 바뀌어 ABI 버전도 올라갑니다.

**워드 경계를 Swift에서 구현한다.** CJK·이모지·하이픈·경로 구분자에 대한
규칙을 엔진과 별개로 갖게 되고, 두 규칙이 어긋나기 시작하면 그 차이를 설명할
문서가 어디에도 없습니다.

**키 매핑을 쓰는 키만 채운다.** `NSEvent.keyCode` → `GhosttyKey` 매핑은 상수
배열 하나입니다. 빠진 키는 `GHOSTTY_KEY_UNIDENTIFIED`로 조용히 떨어져 나중에
원인을 찾기 어렵습니다. 미디어 키는 macOS가 앱에 `keyDown`으로 주지 않아 자연히
빠집니다.

## 결과

- **심볼 10개가 늘고 ABI 버전은 그대로입니다.** 전부 신설이고 기존 시그니처와
  구조체 레이아웃을 건드리지 않습니다. 02-ffi의 동결 규칙이 심볼 추가를
  허용합니다.
- **open-questions 2건이 닫힙니다.** "마우스 리포팅 상태"는 판정이 코어로
  가면서 물을 대상이 없어지고, "전달할 키의 범위"는 질문이 틀렸던 것으로
  드러납니다 — 엔진 열거형이 물리 키라 실제 문제는 매핑을 어디까지 채우느냐이고,
  답은 전부입니다.
- **리사이즈가 셀 픽셀 크기를 받습니다.** `ghostty_terminal_resize`가 요구하고,
  `io.rs`의 `ws_xpixel: 0`도 그때 채워집니다. 자식의 in-band 크기 보고가
  그래야 맞습니다.
- **앱이 오토스크롤 방향을 직접 판정합니다.** 몇 줄이지만 우리 코드이고,
  엔진이 같은 판정을 갖고 있는데 쓰지 않는 자리입니다.
- **상류가 제스처 기계를 개선해도 자동으로 받지 못합니다.** force click 같은
  것이 붙으면 우리가 따로 배선합니다.
- **`ghostty_terminal_select_output`을 쓰지 않습니다.** ⌘클릭으로 명령 출력
  블록을 선택하는 기능이지만 OSC 133 셸 통합 위에서만 의미가 있고, 그것은 v1
  비목표입니다.
- **틀렸을 때의 값이 쌉니다.** 제스처 상태를 앱에 둔 것이 실사용에서 잘못으로
  드러나면 엔진 기계로 가는 길은 심볼 **추가**이지 변경이 아닙니다. ABI 버전은
  그때도 그대로입니다.
