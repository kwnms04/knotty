# VT 엔진 타입은 C ABI 경계를 넘지 않는다

코어가 VT 엔진의 렌더 상태를 knotty 자신의 타입으로 변환해 C ABI로 내보냅니다. 프런트엔드는 VT 엔진의 헤더를 보지 않고, 그 존재도 알 필요가 없습니다.

## 근거

[0001](0001-portable-core.md)에서 C ABI를 이 프로젝트의 이식 가능한 공개 계약으로 정했습니다. VT 엔진의 ABI는 퍼블릭 알파이며 불안정합니다([0002](0002-libghostty-vt-core.md)). 공개 계약이 불안정한 서드파티 ABI를 그대로 투과시키면 계약이 아닙니다 — 업스트림이 흔들릴 때마다 모든 프런트엔드가 같이 흔들립니다.

## 기각안

**통과 (pass-through)** — 그리드·렌더 상태를 VT 엔진의 C 타입 그대로 프런트엔드에 넘기고, knotty-ffi는 세션 수명주기·PTY·이벤트만 덮는 안입니다. 훨씬 작습니다. VT 엔진의 렌더 상태 API는 애초에 호스트 렌더러용으로 설계되었으므로 잘 맞기도 합니다.

기각 사유는 비용 비교가 아닙니다. 프런트엔드가 아직 하나뿐이라 지금의 절연이 투기라는 점, 두 번째 프런트엔드가 생긴 뒤에 감싸도 코어가 이미 중간에 있어 비용이 유계라는 점 — 둘 다 인정합니다. 그럼에도 이식 가능성을 지금 열어두는 쪽을 택했습니다.

## 결과

- 프레임마다 변환 계층을 지납니다. 이 비용은 의도적으로 지불하는 것입니다.
- **이 계층은 "이름만 바꾸는 계층"처럼 보입니다.** 실제로 VT 엔진의 렌더 상태와 knotty의 스냅샷은 모양이 비슷해질 가능성이 높습니다. 그래서 삭제 유혹이 생기지만, 이것이 이 ADR이 존재하는 이유입니다. 지우려면 [0001](0001-portable-core.md)부터 뒤집어야 합니다.
- knotty의 스냅샷 형식을 knotty가 직접 정의해야 합니다. VT 엔진의 렌더 상태 모델을 그대로 베낄지, 다른 모양으로 갈지는 별도 결정입니다.
