# 스냅샷은 코어가 만들어 단일 슬롯 메일박스로 넘긴다

터미널 상태를 두 스레드가 락으로 공유하지 않습니다. 코어가 I/O 스레드를 소유하고 그 안에서 스냅샷까지 만든 뒤, latest-wins 단일 슬롯 메일박스에 놓습니다. 호스트는 받아가기만 합니다.

## 맥락

이전 설계는 그리드를 두 스레드가 공유하는 것이었습니다 — I/O 스레드가 파싱하고 메인 스레드가 스냅샷·입력·선택을 처리하며, 공정(fair) 뮤텍스와 청크마다의 락 양보로 메인 스레드가 굶는 것을 막는 구조였습니다. 그 위에 **"폭주 출력 중에도 메인 스레드의 스냅샷 획득이 유계"(목표 p99 < 1ms)**라는 계약이 얹혀 있었습니다.

`libghostty-vt` 안전 래퍼가 모든 핸들을 `!Send + !Sync`로 표시하므로([0002](0002-libghostty-vt-core.md)) 이 공유 구조는 성립하지 않습니다.

## 근거

- 공정 뮤텍스는 **락 경합을 완화하려고** 존재했습니다. 메일박스 모델엔 그 경합이 없습니다. 호스트는 완성된 스냅샷을 받아가므로 파서와 경쟁하지 않고, 획득이 O(1)로 유계입니다 — 위 계약의 목적을 더 곧게 달성합니다.
- 이식성([0001](0001-portable-core.md)): 코어가 자기 스레드를 소유하면 **호스트의 스레딩 모델을 따지지 않습니다**. AppKit 메인 스레드·GTK 메인 루프·Win32 메시지 펌프가 전부 다른데, 락 공유 모델은 호스트가 코어의 락 규율에 참여할 것을 요구합니다.
- latest-wins 단일 슬롯은 경계를 넘는 정보의 판정 기준과 같은 모양입니다: **최신 값만 의미 있는 것(latest-wins)은 스냅샷으로, 발생 사실 자체가 의미 있는 것(exactly-once)만 이벤트로** 보냅니다.

## 기각안

**`libghostty-vt-sys`로 내려가 자체 `Send` 래퍼를 만들고 공유 그리드를 보존** — 안전 래퍼를 버려야 하고, 하부 C 라이브러리가 실제로 다중 스레드 접근을 허용하는지도 미확인입니다. 무엇보다 살리려는 그 설계가 메일박스 모델에선 불필요합니다.

## 결과

- 공유 그리드 락 설계와 **공정 뮤텍스 요구가 사라집니다.**
- "폭주 중 스냅샷 획득 p99 < 1ms" 성능 게이트는 목적은 유지하되 측정 대상이 바뀝니다 — "락 대기 + 복사"가 아니라 "메일박스 수신"입니다.
- 스냅샷 생성 비용이 I/O 스레드로 이동합니다. 프레임이 필요 없을 때 낭비되지 않도록 메일박스는 wake당 최대 1회만 채웁니다.
